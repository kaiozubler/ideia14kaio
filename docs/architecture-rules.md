# Existing architecture rules

- Integra BRy stores the `/psc/link` response `token` as the session X-API-KEY; `state` is only a callback correlation value, because BRy rejects `state` as a credential.
- Integra BRy link sessions persist the same lifetime sent to `/psc/link`, because the local expiry must not invalidate a still-authorized PSC session.
- Integra BRy PDF signing uses the HUB Signer endpoint with `kms_type: PSC` and `kms_data: { url, token }`, because X-API-KEY is only for the Integra authentication-information endpoints.
- Server-side PDF generation uses pure JavaScript libraries only, because native browser binaries are unavailable in the production runtime.
- Protocols are authored in the Studio (`public/protocolo-studio.html`) and published by compiling the graph into `protocolo_acoes`/`protocolo_regras` through `salvar_protocolo`, because the task/exam/alert engine only executes that relational model.
- Studio publishing stores a graph-key → uuid map in `protocolo_estudio_rascunhos.publicacao` and resends those uuids, because recreating actions cascades away patients' task history.
- Conditions the engine cannot evaluate (medication state, pregnancy/weight, AND across different exams) and same-group drug alternatives compile to "Decidir"/"Escolher" alert tasks whose rules match the doctor's choice as `{texto: <branch id>}`, because silently dropping those branches would lose treatment lines.
- The clinic ↔ patient WhatsApp channel (Conversas screen) uses each clinic's own Meta Cloud API credentials, stored AES-GCM-encrypted in `comunicacao_whatsapp_conexoes`, never the global `WHATSAPP_*` env vars, because those belong to the app's single number used by the doctor ↔ assistant channel.
- Clinic webhooks are served at `/api/public/webhooks/whatsapp-clinica/<webhook_chave>` and require the clinic's App Secret, because Meta's GET verification carries no `phone_number_id` and an unsigned URL would let anyone inject fake patient messages.
- Message templates are written only through `/api/comunicacao/modelos`, because their status mirrors Meta's review; free-form sends are blocked outside the 24h customer-service window, where documents fall back to the template chosen in `comunicacao_whatsapp_automacoes.documento_modelo_id`.
- Faturamento keeps `lancamentos_financeiros` as the single ledger of receipts and payments; services (`faturamento_servicos`), their occurrences (`faturamento_execucoes`), billing clients (`faturamento_clientes`, distinct from patients) and invoices (`faturamento_notas`) hang off it, because the screen must show the same money per work, per client, per NF and per receipt.
- Recurring services always keep the next 6 open receipts materialized (topped up on screen load, unique on `servico_id, competencia_inicio`), and a receipt edited individually (`editado = true`), received, or linked to an NF is never recalculated when the service changes, because users adjust single future payments by hand.
- NF emission is decided per receipt by `nf_modo` (each service, every 15 days, monthly, on authorization, none); biweekly/monthly modes group the client's receipts of the closed period into one `faturamento_notas` row, and NF numbers are internal control numbers until an NFS-e provider is integrated.
- Prescription document rules live in `public/receituario-controlado.js` (Portaria 344 lists plus their adendos by dose/form, `substancias.retencao_receita` for antimicrobials/GLP-1); each document type (common, Controle Especial, retained 2-copy, one notification per drug) is a separate PDF, because the pharmacy must retain only what the norm requires.
- Notificações de Receita are generated only as watermarked transcription mirrors with the doctor's talonário number, because without SNCR integration (RDC 1.000/2025) a self-printed or unnumbered notification is not valid for dispensing.
- PDFs that fail ICP-Brasil signing are re-rendered with a blank handwritten-signature line instead of the "assinado digitalmente" seal, because an unsigned document must not claim a digital signature.
- An active Integra BRy link session signs instead of the `doctor_certificates` row when it is newer or that certificate is expired, because the sign-time reconnect overlay would otherwise link a certificate that is never used.
- Every PDF from `_renderDocumentoPdf` (and the exam request) reserves a `documentos_verificacao` row before rendering and prints a QR with the authenticated link `/v/<codigo>?k=<token>` plus the short link `/v/<CODIG-O>` opened with the patient's last 4 CPF digits; only hashes of token and password are stored and failed password attempts are inserted before being counted, because 4 digits are only 10k combinations and parallel requests must not bypass the limit.
- The verification page reads signer, CA, serial and integrity from the PDF stored server-side by `/api/documentos/verificacao/emitir`, never from the browser, because the page must prove what was actually signed.
- Document PDFs render the whole scoped holder (not the bare `.sheet`) with a `:where(#scope) *` reset and `.sheet { min-height: 296mm }`, because html2pdf clones the element out of the scope (default margins grow the sheet past A4) and 297mm rounds up into a blank trailing page.
- The Atendimentos kanban (`public/atendimentos-kanban.js`) keeps stages in `atendimento_etapas` and cards in `atendimento_fluxo`, never in localStorage, because reception, triage and the doctor's office use the same account on different computers and must see one board (synced through Supabase realtime).
- A scheduled appointment appears as a virtual card in the `agendado` stage and only gets an `atendimento_fluxo` row on its first action (unique on `agendamento_id`), because materializing every appointment would duplicate the agenda; stage timestamps come from the database clock and history from the `atendimento_fluxo_eventos` trigger, so wait times agree across machines.
- Stage `tipo` carries the semantics (only one `agendado` and one `concluido` per clinic); a stage's `encaminhar_para` applies only after its own shortcut action, while "atender" and "finalizar" fall back to the consultório/concluído stages, because entering a stage must not chain-forward a card that just arrived.
- "Salvar e finalizar" in the prontuário moves the patient's active card to the `concluido` stage and sets `agendamentos.status = 'atendido'`, because finishing the consult is the doctor's signal that the patient was seen.
- Kanban charges are `lancamentos_financeiros` receipts (`origem = 'consulta'`) and a card's paid state is read from that row, because Faturamento is the single ledger.
- The clinic is the doctor's account; secretaries and nurses log in with their own accounts linked through `clinica_membros` (role kept server-side, never in `user_metadata`), and `clinica_id()`/`papel_clinica()` scope extra RLS policies only on agenda, kanban, triage (nurse) and consultation receipts (secretary), because the prontuário, consultations, exams and documents must stay unreadable to the team even outside the UI.
- The team reads patients only through the `pacientes_cadastro` view and writes them through `paciente_cadastro_salvar`, because Postgres RLS cannot hide columns and `dados_clinicos`, `info_complementar`, `cids` and `parentescos` are clinical data.
- Team invites are links with a random token (only its SHA-256 is stored, 7-day expiry) accepted on login by the invited e-mail, and count against the plan's `secretarias` licenses, because the app has no transactional e-mail and the link alone must not grant access.
- Rows a team member creates default `id_medico`/`user_id` to `clinica_id()`, and client inserts use `clinicaId()`, because data belongs to the clinic, not to the login that typed it.
- Triage is optional per clinic (`medico_clinica_config.triagem_ativa`, Minha clínica); when off, triage stages are hidden and cards or forwards pointing to them continue to the stage's `encaminhar_para`, because turning the switch must not strand patients already in triage.
- The doctor sees the day's triage inside the consultation (prontuário › Atendimentos) with "Inserir no prontuário" and can add a triage there without a kanban card (`fluxo_id` null), because the triage belongs to the consult, not to a separate patient tab.
- Manual WhatsApp confirmations (`/api/comunicacao/confirmar-agendamento`) reuse the automatic job's `comunicacao_whatsapp_envios_automaticos` reservation and move the appointment to `confirmacao_enviada`, because the patient must not receive the same confirmation twice.
- Readable Anvisa presentation texts (`apresentacao_legivel`) are written by Claude offline via `scripts/apresentacoes.mjs` and imported through `/api/medicamentos/simplificar-apresentacoes`, gated by `CATALOGO_ADMIN_TOKEN` and rejecting any number absent from the original, because the catalog is shared by every clinic and the rewrite must never change a dose.
- Clinical records (`consulta` once finalized, `exames`, `triagens`, `documentos_paciente`, `medicamentos_em_uso`) are never deleted, and a patient can be deleted only while they have none of them; a BEFORE DELETE trigger rejects it for every role, and a restrictive storage policy blocks deleting `exames-arquivos`/`documentos-arquivos` files, because the record must be kept for 20 years (Lei 13.787/2018).
- Every insert or update of those tables (and of `pacientes`) writes a full snapshot to the append-only `prontuario_versoes` (author name and CRM/COREN resolved server-side; reason taken from the transient `motivo_alteracao` column, which the trigger clears), because edits must keep the original and each change readable on screen and in print. Draft consultations (`acao = 'Rascunho'`) are not versioned and can be discarded until first finalized, and a finalized consultation cannot be turned back into a draft.
- The patient merge (`/api/pacientes/migrar`) must list every table that holds clinical rows, because the origin patient can only be deleted once nothing clinical points to it.
- The prontuário export (`public/prontuario-exportar.js`) renders through `_renderDocumentoPdf` with `assinar: false` for print/download, and only "Assinar e enviar" signs, stores the PDF as a `documentos_paciente` row of `tipo = 'prontuario'` and sends it through `/api/comunicacao/enviar`; an export whose ICP-Brasil signing fails is downloaded but never sent, because the patient must not receive an unsigned copy presented as signed.
- Dark mode (`public/tema-escuro.css` + `public/tema-escuro.js`) redefines the `--n*`/`--g*`/`--white` tokens and converts hard-coded colors of stylesheets and `style=""` at runtime, keeping each original to restore light without reload; the choice is saved per login in `user_metadata.tema` (localStorage is only a pre-login cache), because secretaries and the doctor share a clinic but not a preference.
- Document sheets (`.ia-prev-sheet`, the `rx-/lme-/ex-scope-*` and `ia-rx-/ia-ex-*` holders, `.html2pdf__overlay`) and the template `<style>` injected for them are never converted, and printing switches back to light, because PDFs and prints must stay black on white paper.
- Screen tours (`public/tour-guiado.js` + `.css`) open automatically once per screen per login, tracked in `user_metadata.tours_vistos`, and the topbar "?" reopens or restarts the tour of whichever screen is visible; steps whose target is hidden or doctor-only for a team member are skipped, because the same tour serves every role and every empty or loading state.
- The prontuário export, print and "Assinar e enviar" refuse a patient without a valid CPF (checked on the screen copy and again on the row loaded from the database), and the PDF lists the Res. CFM 1.638/2002 identification fields (patient, establishment with CNPJ, doctor with CRM/UF) printing "não informado" when one is empty, because the QR verification needs the CPF and a missing required field must be visible instead of silently omitted.
- The doctor's CRM is read through `_medicoCrm(meta)` (`crm_numero`/`crm_uf`, written by Minha equipe, with `crm` as legacy fallback) in every PDF, in `getDoctorInfo` and in `prontuario_nome_autor`, because reading only `meta.crm` printed "CRM —" for doctors who set their CRM in the profile.
- Patient `naturalidade` (birth município/UF) is a cadastral field: it is exposed in `pacientes_cadastro` and accepted by `paciente_cadastro_salvar`, and the prontuário PDF prints it as a required field, because Res. CFM 1.638/2002 lists it in the patient identification and the team edits the cadastro.
- The doctor's specialty prints on documents only together with the RQE (`user_metadata.especialidade` + `rqe`, set in Minha equipe › perfil) through `_medicoEspecialidade(meta)` and `getDoctorInfo`, because Res. CFM 2.336/2023 forbids announcing a specialty without its RQE.
- The clinic's public booking link is `/agendar/<token>` (`agenda_online_config`, revoked by generating a new token) and reads only through `/api/public/agendamento/*`, which return free instants and never who holds the others; it stops working when switched off, when the clinic is in `acessos_bloqueados` or has no active subscription, because the page runs without a session on `supabaseAdmin`.
- Doctors live in `agenda_medicos` (the account owner is created by `agenda_online_preparar`, active rows count against `assinaturas.medicos`), and both the Agenda and the public link read that list, because the clinic is a single login and `clinica_membros` only holds secretaries and nurses.
- A public slot exists only inside the clinic's hours, inside the doctor's own hours (`horarios` null means all clinic hours) and clear of any appointment; an appointment with `agenda_medico_id` null blocks every doctor of the clinic, because older rows and the prontuário's return shortcuts carry no doctor and must never be double-booked. Hours are in Brasília time regardless of server or patient timezone.
- `agenda_publica_reservar` rechecks conflicts under a per-clinic advisory lock and is `service_role` only; the route first checks the requested instant against the computed grid, because the browser's value cannot be trusted and two patients can pick the same slot at once.
- The public link never changes an existing patient (a typed CPF proves nothing) and answers the same for new and known CPFs; name and phone are restricted to characters that cannot form markup, because the Agenda and Atendimentos screens render them with `innerHTML`.
- The public page shows a doctor's specialty only with the RQE, because Res. CFM 2.336/2023 forbids announcing a specialty without it.
- Smartphone audio capture (`public/captacao-smartphone.js` + `/captar`) is opened and resumed only by the logged-in computer (`/api/captacao-movel`); the phone, authenticated only by the QR token (in the URL fragment, stored as SHA-256 in `captacao_movel_sessoes`, 5 min to scan, 4 h max call), can only connect, send and end, because a leaked or reused QR must never start a recording.
- The phone transcribes directly on Deepgram (or, in basic transcription, with the phone browser's speech recognition) with the same parameters as the local recording and posts finals, partial text and audio level to `/api/public/captacao-movel`; the computer reads them through Realtime with owner-only RLS and feeds `addTranscriptLine`, so the copilot runs unchanged with a single audio source at a time (connecting the phone stops the local mic).
- `/api/chat-ia` and `/api/deepgram-token` require a valid Supabase `Authorization: Bearer` token (the app sends it through `iaAuthFetch` in `medicopilot.html`), and the chat's knowledge base uses that verified user, never `body.user_id`, because each call spends the account's Gemini/Deepgram keys and the `anamnese` mode accepts a free system prompt; the phone and the extension get Deepgram tokens only through their own authenticated public routes.
- Consult transcription is "avançada" (Deepgram) only for Pro/Enterprise subscriptions whose `user_metadata.transcricao` is not `basica`, decided server-side by `modoTranscricao` in `/api/deepgram-token` and the phone route (403 `transcricao_basica` otherwise); "básica" uses the browser's Web Speech API, because Deepgram is billed per minute and the browser cannot be trusted to state its own plan.
- Deepgram streams (computer and phone) stop sending audio after 2 s below ~-48 dBFS and keep the socket alive with `KeepAlive`, resuming on the first voice frame; the level is measured on the audio thread and a doctor's pause always wins, because silence is billed audio and timers are throttled in background tabs.
- The copilot's automatic cycle calls the AI only with at least 40 new spoken words (bracketed system lines excluded), because a call without new speech cannot produce a new suggestion.
- `/api/chat-ia` answers with the model chosen in `user_metadata.ia_analise` (`gemini` = `GEMINI_MODEL` via the Lovable gateway, `claude` = `claude-sonnet-5-5` via the Anthropic SDK with server-side refusal fallback, falling back to Gemini when `ANTHROPIC_API_KEY` is unset); every Gemini call in the app uses the single `GEMINI_MODEL` constant in `src/lib/ia/provedor.server.ts`, because the gateway retires model IDs and one place must change them.
